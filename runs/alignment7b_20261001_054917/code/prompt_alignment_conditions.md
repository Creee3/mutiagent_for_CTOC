# 同输入的文本与KV核对

目的很简单：上一轮全文文本和KV用了不同聊天格式。先检查相同模型、相同token、相同解码时，完整KV和直接输入文字是否实际上给出同样结果。

学校服务器已有kv-graph conda，已有且核验过的Qwen2.5-7B-Instruct；一份冻结权重，BF16、SDPA、batch=1、greedy，原生EOS，答案上限48，完整28层KV，shift_back=False。没有安装依赖或调整系统CUDA。

使用data/calibration.json按原顺序前10题。第11题只作预热。评测100题和预留500题不使用；这10题的评分只是方便查看答案，不用来确认优势或调参数。

| 诊断条件 | 输入 | 重复惩罚 |
| --- | --- | --- |
| skyline_p105 | 原版全文文本：一套材料+问题的chat | 1.05，原生全输入范围 |
| concat_p105 | 官方KV的A输入token与B输入token直接拼接 | 1.05，原生全输入范围 |
| concat_bscope_p105 | 同上 | 1.05，仅B输入和已生成token，与CV范围一致 |
| kv_p105 | 官方A材料prefill，然后CV读取B输入 | 1.05，原版CV范围 |
| skyline_p1 | 原版全文文本格式 | 1，关闭重复惩罚 |
| concat_p1 | 与KV完全相同的A+B token | 1，关闭重复惩罚 |
| kv_p1 | 官方完整KV | 1，关闭重复惩罚 |

直接拼接的是已经生成的token ID，不先解码再重新分词，以免边界变化。对齐惩罚条件只在独立脚本加一个处理器，官方源码和主实验配置不改。每次KV调用重新形成发送方缓存，防止上一条件的解码污染缓存。

每题7次生成，共70个诊断答案。第11校准题做concat_p1、kv_p1两个预热答案，总生成72次；KV生成额外调用A prefill共21次。每题另外用三次显式forward比较raw logits（拼接、A prefill、CV读B），共30次；总显式非生成forward为51次，其中A prefill共31次。模型生成内部的逐token forward不重复算成回答调用。

保存A/B/拼接/原版输入token、完整输出token与文本、EOS和触顶、第一处输出差异、raw logits差值和top1一致率、输入hash、版本、GPU、逐次调用账目。BF16两次prefill与一次prefill可能有数值舍入差异，因此不预设7B必须逐位一致；数值误差和输出差异如实报告。耗时仅诊断记录，不用本轮证明加速。

启动前先用随机CPU小Qwen确认自定义惩罚处理器和缓存路径；真实7B仍在服务器GPU运行。结果写入独立alignment7b_*目录，不覆盖前一轮。预期比较顺序：先看无惩罚的拼接与KV，再看对齐作用范围后的拼接与KV，最后看原版全文与拼接，分清缓存接入、解码、提示格式各自的影响。
