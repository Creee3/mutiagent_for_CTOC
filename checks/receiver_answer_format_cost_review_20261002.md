# 短答案检查：强文本与成本

2026-10-02，只读检查与CPU条件建议。本文件不启动模型，不改旧输入、代码或结果。

**四方法可以这样设。强文本直接提供完整A材料，作为正常工作流对照；精确token全文与完整KV用来比较同一输入的两种接入。** 两类比较要分别解释。

| 方法 | 接收方看见什么 | 必需的A模型计算 |
| --- | --- | --- |
| 无消息 | B自己的材料和该状态下已经持有的A材料 | 无 |
| 精确token全文 | 同一B输入，加canonical A来源前缀 | 无，直接复制已准备的token IDs |
| 完整KV | 同一B token数组，接续同一个A前缀的完整cache | A prefill；已有cache场景单列 |
| 强文本 | 单份共同system规则、正常B输入，另加入原样完整A材料 | 无，直接复制材料 |

所有方法保留B已经持有的材料。强文本收到的A标题、句子、顺序和原始文字应完整相同；本轮不根据full/partial标签、支持标注或金标隐藏删掉重复段。问题由正常B输入给出；若省去再次复制A问题，记录为工作流差异，不称新信息删减。A的角色指令已经移除，因此强文本不需要额外携带“提取三句”的任务。

共同system明确只给答案短语、日期、数值或yes/no，不复述题目、不解释；不能含题目特定正确例子。模型输入只由材料、问题和统一规则构造，金标仅留给事后既有评分。三状态只配对相同6题：18份输入×4方法=72次主回答；如做4次预热则共76次generate。A主来源6次prefill、独立预热1次，共7次；不会额外给两条文本或无消息路线做A forward。这是待冻结的账本，尚非实际执行记录。

## 消息字节怎么记

强文本的消息内容是**发送的完整A材料UTF-8字节**。B本地材料、已持有材料及本地共同system不算A→B发送量，但要记录它们的接收输入tokens和驻留量。若真实协议还发送问题、角色、来源编号或校验值，按实际包计入；不能只报材料字节而忽略这些字段。

给强文本真正编码包：固定编码/framing，存实际包长与SHA，分别列UTF-8内容、包头和总字节。不要只用`len(text)`或口算“内容+估计包头”。精确token包另记int32内容和头；KV包另记tensor、来源token IDs和头。不要把含token IDs的KV包称裸KV。实验审计字段与协议必需字段可以分项列出，不能只给某一路算审计开销。

强文本与完整token包大小不同，既有编码差异，也有内容组织差异：token前缀带共同system、来源问题及chat边界，强文本发送原材料，由接收方本地组织。它是实用工作流基线，不是同数组传输编码的严格替换。应保留这两个文本对照，而不是把强文本token数强行配成A+B长度。

## 计算成本怎么记

文本不要承担无必要A prefill。KV从零开始计A prefill、编码、恢复、B prefill/解码；cache预先存在时另报接收阶段，并说明来源cache如何产生、是否计驻留。实际复用6份来源服务18份接收视图，与18个独立KV请求各重做A的成本估算分别列出。

强文本需要接收侧解码UTF-8、组织正常B输入并tokenize。若本轮预先冻结了token数组，主GPU时钟不包含这部分；其他方法的输入准备同样不能只在一边计入。可以统一报“prompt/token就绪后的模型与包编解码阶段和”，再单列真实输入构造/tokenization成本。不能把预计算的强文本tokenization说成免费，也不能把只给强文本新增的准备耗时混入另一条prompt-ready计时。

单次短检查首先看格式遵守、EOS/触顶和既有EM/F1是否可读；不同输出长度的总时长不能纯归因于cache。未测真实网络，不称网络加速；未做删减，不称压缩收益。

## 以后能不能做文本精确去重

可以，**作为下一项独立基线**。规则只比较发送的完整材料块与接收方显式可见文字；例如同标题下完整相同句块，确认上下文一致才不重复发送。不读取held标注、condition或金标，不把相似句子当相同事实，也不截掉解释剩余文字所需的标题/指代。

先保留本轮完整强文本，再另列“可见文字精确去重文本”，存去掉的字节范围、匹配位置和规则；不默默改变本轮完整消息。若A原本不知道B持有什么，要计B→A的内容/哈希请求及选择成本，不能靠离线调度标签免费获知。接收方本地删除已经收到的重复文字可以少prefill，但**不能倒算为少传**。该基线只验证精确重复，不能直接当语义增量算法或论文创新。
